# DESIGN SYSTEM — SIMOKP
## Sistem Informasi Manajemen Oplah, Kerja Sama, dan Kinerja Pemasaran

**Versi:** 1.0  
**Jenis aplikasi:** Responsive Web Dashboard  
**Gaya desain:** Professional Corporate Dashboard  
**Bahasa antarmuka:** Bahasa Indonesia  
**Target perangkat:** Desktop, tablet, dan mobile

---

# 1. Konsep Desain

## 1.1 Arah Visual

SIMOKP menggunakan desain dashboard profesional yang mengutamakan:
- Kejelasan informasi.
- Kemudahan navigasi.
- Efisiensi input data.
- Konsistensi tampilan.
- Kemudahan membaca laporan.
- Hierarki informasi yang jelas.
- Penggunaan warna secara fungsional.

Aplikasi harus terasa seperti sistem manajemen perusahaan media, bukan website berita publik.

## 1.2 Karakter Desain

- Profesional.
- Modern.
- Bersih.
- Terstruktur.
- Informatif.
- Tidak terlalu dekoratif.
- Mengutamakan data dan tindakan.

## 1.3 Prinsip UX

1. Pengguna dapat memahami halaman tanpa pelatihan panjang.
2. Informasi terpenting ditampilkan lebih dahulu.
3. Form dibagi menjadi beberapa bagian logis.
4. Tindakan penting membutuhkan konfirmasi.
5. Status selalu terlihat jelas.
6. Kesalahan input dijelaskan secara spesifik.
7. Tabel mendukung pencarian, filter, sortir, dan pagination.
8. Tampilan menyesuaikan permission pengguna.

## 2.1 Palet Warna

Warna utama menggunakan navy, biru, dan teal.

| Token | Warna | Penggunaan |
|---|---|---|
| Primary | #1E3A5F | Navigasi dan tombol utama |
| Primary Light | #EAF1F8 | Background aktif |
| Secondary | #2878B5 | Link dan elemen sekunder |

| Warning | #D99026 | Perlu perhatian |

| Info | #2780B9 | Informasi |

## 2.2 Aturan Penggunaan Warna

- Primary untuk aksi utama.
- Success untuk status berhasil.
- Warning untuk proses tertunda.
- Danger untuk penolakan dan tindakan berisiko.
- Info untuk informasi netral.
- Warna status harus dilengkapi teks atau ikon.
- Jangan menggunakan banyak warna aksen dalam satu halaman.

## 2.3 Tipografi

Font utama: Inter.

Fallback:
- system-ui
- Arial
- sans-serif

Ukuran:
- Page title: 24–28 px.

- Card title: 14–16 px.
- Body: 14 px.
- Table: 13–14 px.
- Caption: 12 px.
- Form label: 13–14 px.

Bobot:
- Regular 400.
- Medium 500.
- Semibold 600.
- Bold 700.

- Realisasi.
- Event.
- Keuangan.
- KPI.
- Laporan.
- Pengaturan.
- Audit.

Permission dapat diberikan melalui checkbox.

## 17.4 Permission Tambahan

Untuk karyawan tertentu, Super Admin dapat memberikan akses tambahan atau pembatasan.

Contoh:
- Karyawan pemasaran boleh melihat laporan keuangan tertentu.
- Karyawan keuangan boleh memverifikasi pembayaran.
- Karyawan sirkulasi boleh memvalidasi retur.

Perubahan permission harus dicatat dalam audit log.

# 18. Desain Audit Log

Tabel:
- Waktu.
- Pengguna.
- Modul.
- Aktivitas.
- ID data.
- Ringkasan perubahan.
- Aksi detail.

Detail:
- Data sebelum.
- Data sesudah.
- Pengguna.
- Timestamp.
- Alasan perubahan.

Audit log bersifat read-only bagi pengguna yang memiliki izin melihatnya.

# 19. Desain Responsive

## 19.1 Desktop

- Sidebar tetap.
- Topbar penuh.
- Tabel menggunakan lebar maksimal.
- Dashboard dapat menggunakan 3–4 kolom KPI.
- Form menggunakan 2 kolom bila sesuai.

## 19.2 Tablet

- Sidebar dapat collapse.
- KPI menjadi 2 kolom.
- Form menjadi 1–2 kolom.
- Tabel dapat menggunakan horizontal scroll.

## 19.3 Mobile

- Sidebar menjadi drawer.
- Topbar ringkas.
- KPI menjadi 1–2 kolom.
- Form satu kolom.
- Tombol aksi utama mudah dijangkau.
- Tabel kompleks dapat berubah menjadi list/card.
- Input file dan foto harus mudah digunakan.

Breakpoint acuan:
- Mobile: sampai 767 px.
- Tablet: 768–1023 px.
- Desktop: mulai 1024 px.

---

# 20. UX State

Setiap halaman harus memiliki:

## Loading
- Skeleton card.
- Skeleton table.
- Indikator proses pada tombol.

## Empty State
Contoh:
"Belum ada proposal kerja sama."

Sediakan tombol:
"Buat Proposal".

## Error State
- Pesan kesalahan yang jelas.
- Tombol coba lagi jika relevan.
- Jangan menampilkan stack trace kepada pengguna.

## Success State
- Konfirmasi berhasil.
- Informasi data yang berhasil disimpan.
- Navigasi ke halaman detail jika relevan.

## Validation State
- Field bermasalah diberi indikator.
- Pesan kesalahan spesifik.
- Fokus diarahkan ke field pertama yang bermasalah.

---

# 21. Form UX dan Validasi

Aturan:
- Field wajib ditandai.
- Format angka rupiah konsisten.
- Tanggal menggunakan format lokal Indonesia.
- Nomor dokumen dibuat otomatis.
- Select memiliki pencarian jika data banyak.
- Upload menampilkan nama dan ukuran file.
- Form panjang menggunakan section atau stepper.
- Data draft dapat disimpan.
- Perubahan yang belum disimpan diberi peringatan ketika pengguna keluar.

Untuk proposal:
- Nilai tunai dan barter diinput terpisah.
- Total nilai dihitung otomatis.
- Rincian barter harus sesuai total nilai barter.
- Lampiran dapat ditambahkan.
- Tombol ajukan tidak aktif jika data wajib belum lengkap.

Untuk retur:
- Distribusi asal wajib dipilih.
- Jumlah retur tidak boleh melampaui sisa kuantitas yang dapat diretur.

Untuk pembayaran:
- Nominal tidak boleh negatif.
- Pembayaran tidak boleh melebihi sisa tagihan kecuali perusahaan mengaktifkan mekanisme uang muka/kelebihan pembayaran.

# 22. Interaksi Penting

## 22.1 Persetujuan Proposal

- Admin membuka daftar proposal.
- Memilih proposal.
- Memeriksa rincian.
- Memilih Setujui, Tolak, atau Minta Revisi.
- Sistem menampilkan dialog konfirmasi.
- Admin mengonfirmasi.
- Sistem menyimpan keputusan dan audit log.
- Karyawan menerima notifikasi.

## 22.2 Pengajuan Proposal

- Karyawan mengisi form.
- Menyimpan draft.
- Memeriksa ringkasan.
- Mengajukan proposal.
- Sistem memvalidasi.
- Status berubah menjadi Diajukan.
- Admin menerima notifikasi.

## 22.3 Pencatatan Retur

- Karyawan memilih distribusi.
- Sistem menampilkan jumlah awal dan sisa kuantitas.
- Karyawan menginput retur.
- Sistem memvalidasi.
- Stok diperbarui sesuai kondisi.
- Riwayat retur tersimpan.

## 22.4 Pembayaran

- Karyawan keuangan membuka invoice.
- Memilih catat pembayaran.
- Mengisi nominal dan bukti.
- Pembayaran masuk status menunggu verifikasi jika diperlukan.
- Pengguna berwenang memverifikasi.
- Piutang diperbarui.
